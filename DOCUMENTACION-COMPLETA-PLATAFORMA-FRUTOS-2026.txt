3.1 SISTEMA LOBO SOLITARIO (Completado ✅)
--------------------------------------------------------------------------------

**Descripción:** Programa individual de 63 días (9 semanas) sin visión 
organizacional.

**Características:**
- **Planes disponibles:**
  - STANDARD Bimestral: 18 sesiones, $1,499 MXN
  - STANDARD Anual: 108 sesiones, $14,999 MXN
  - PREMIUM Bimestral: 18 sesiones, $2,499 MXN
  - PREMIUM Anual: 108 sesiones, $19,999 MXN

**Flujo implementado:**
1. Usuario va a `/dashboard/lobo-solitario/seleccionar-mentor`
2. Selecciona mentor de lista disponible
3. Sistema verifica si ya tiene paquete activo (prevención de duplicados ✅)
4. Usuario selecciona plan (STANDARD/PREMIUM) y frecuencia (BIMESTRAL/ANUAL)
5. Integración con Stripe para pago
6. Tras pago exitoso, crea `MentorPackageOrder` con status COMPLETED
7. Crea `PackageSessionCredits` con sesiones correspondientes
8. Redirecciona a `/dashboard/program/enroll?action=select-mentor`
9. Usuario agenda sus 2 sesiones semanales fijas

**Archivos clave:**

/app/api/lobo-solitario/crear-paquete/route.ts
/app/api/lobo-solitario/verificar-paquete-activo/route.ts
/app/api/lobo-solitario/create-checkout-session/route.ts

**Estado actual:**

5.4 Cálculo de Duración de Programas
--------------------------------------------------------------------------------

// Lobo Solitario
if (packageCredits) {
  totalWeeks = 9;
  totalCalls = packageCredits.totalSessions; // 18 o 108
}

// Programa con fechas explícitas
else if (enrollment.cycleStartDate && enrollment.cycleEndDate) {
  const diffInDays = Math.ceil(
    (endDate.getTime() - startDate.getTime()) / (1000 * 60 * 60 * 24)
  );
  totalWeeks = Math.ceil(diffInDays / 7);
  totalCalls = totalWeeks * 2;
}

// Por tipo de ciclo
else {
  switch(enrollment.cycleType) {
    case 'INTENSIVE_17_WEEKS': 
      totalWeeks = 17; totalCalls = 34; break;
    case 'INTENSIVE_6_MONTHS': 
      totalWeeks = 26; totalCalls = 52; break;
    case 'SOLO': 
      totalWeeks = 8; totalCalls = 16; break;
    default: 
      totalWeeks = 8; totalCalls = 16;
  }
}

   - Función isMaskedValue() que detecta:
     * Asteriscos (*)
     * Puntos de contraseña (•)

   - Evita sobreescribir secretKey con valor enmascarado

e) Mejor logging de errores:
   - Logs detallados en cada paso
   - Stack trace en caso de error

Código de detección de enmascaramiento:
```typescript
const isMaskedValue = (value: string | null | undefined): boolean => {
  if (!value) return true;
  if (value.includes('*') || value.includes('•') || value.includes('·')) return true;
  const chars = value.split('');
  const charCount = chars.reduce((acc, char) => {
    acc[char] = (acc[char] || 0) + 1;
    return acc;
  }, {} as Record<string, number>);
  const maxCount = Math.max(...Object.values(charCount));
  if (maxCount > value.length * 0.5 && value.length > 10) return true;
  return false;
};
```

10. PAYMENT GATEWAY - FIX CONSTRAINT ÚNICO (CAUSA RAÍZ)
================================================================================

Problema raíz identificado:
- La base de datos tenía: organizationId Int @unique
- El schema de Prisma tenía: @@unique([organizationId, provider])
- Discrepancia causaba que solo se pudiera tener UNA pasarela por organización

Solución aplicada (sin pérdida de datos):
```sql
-- Eliminar constraint antiguo
ALTER TABLE "PaymentGatewayConfig" 
  DROP CONSTRAINT IF EXISTS "PaymentGatewayConfig_organizationId_key";

-- Crear nuevo constraint compuesto
ALTER TABLE "PaymentGatewayConfig" 
  ADD CONSTRAINT "PaymentGatewayConfig_organizationId_provider_key" 
  UNIQUE ("organizationId", "provider");
```

Archivo de migración creado:
- prisma/migrations/20260226_fix_payment_gateway_constraint/migration.sql

Resultado:
- ✅ 2 registros existentes conservados
- ✅ Ahora se pueden tener múltiples proveedores (Stripe + MercadoPago) por org
- ✅ El constraint permite: una config por combinación (organizationId, provider)

LECCIÓN IMPORTANTE:
- Siempre verificar que el schema de Prisma esté sincronizado con la BD real
- Usar `npx prisma db pull --print` para ver el estado real de la BD
- Las migraciones manuales deben documentarse en prisma/migrations/

11.3 SISTEMA DE FILTRO POR ÁREA EN /dashboard/hoy
--------------------------------------------------------------------------------

Se implementó filtrado de tareas por área usando URL params:

URL: /dashboard/hoy?area={areaKey}

Áreas soportadas (areaKey):
- finanzas, relaciones, talentos, pazMental
- ocio, salud, servicioTrans, servicioComun

Implementación en page.tsx:
```typescript
// Imports necesarios
import { useSearchParams } from 'next/navigation';

// Estado del filtro
const searchParams = useSearchParams();
const areaParam = searchParams.get('area');
const [areaFilter, setAreaFilter] = useState<string | null>(areaParam);

// Mapeo de área key a valores posibles en el campo area de las tareas
const areaKeyToAreaValues: Record<string, string[]> = {
  'finanzas': ['Finanzas', 'finanzas', '💰 Finanzas'],
  'relaciones': ['Relaciones', 'relaciones', '❤️ Relaciones'],
  'talentos': ['Talentos', 'talentos', '🎯 Talentos'],
  'pazMental': ['Paz Mental', 'pazMental', 'paz_mental', '🧘 Paz Mental'],
  'ocio': ['Ocio', 'ocio', '🎮 Ocio'],
  'salud': ['Salud', 'salud', '💪 Salud'],
  'servicioTrans': ['Servicio Transformacional', 'servicioTrans', ...],
  'servicioComun': ['Servicio Comunitario', 'servicioComun', ...],
};

// Función de filtrado
const filterTasksByArea = (taskList: Task[]) => {
  if (!areaFilter) return taskList;
  const validAreas = areaKeyToAreaValues[areaFilter] || [areaFilter];
  return taskList.filter(task => 
    validAreas.some(areaValue => 
      task.area?.toLowerCase().includes(areaValue.toLowerCase())
    )
  );
};

// Aplicar a las tareas
const filteredTasks = filterTasksByArea(tasks);
const filteredTareasRetrasadas = filterTasksByArea(tareasRetrasadas);
```

Banner visual del filtro activo:
- Muestra el icono y nombre del área filtrada

12.2 FIX: Tareas servicioTrans sincronizadas incorrectamente
--------------------------------------------------------------------------------

PROBLEMA:
El sync de tareas de enrolamiento marcaba TODAS las tareas como completadas
sin verificar el número real de invitados. Ejemplo: Usuario con 2 invitados
mostraba 4/4 tareas completadas al 100%.

CAUSA:
El script de sync completaba todas las TaskInstance de servicioTrans sin
contar cuántos invitados reales tenía cada usuario.

SOLUCIÓN:
Script de corrección que:
1. Cuenta invitados reales por usuario (SELECT COUNT WHERE invitedBy = userId)
2. Resetea todas las tareas de servicioTrans a PENDING
3. Marca como COMPLETED solo el número de tareas igual a invitados reales

LÓGICA CORRECTA:
```javascript
// Contar invitados reales
const realInvitees = await prisma.usuario.count({
  where: { invitedBy: user.id }
});

// Si tiene 4 tareas pero solo 2 invitados:
// - 2 primeras tareas → COMPLETED
// - 2 últimas tareas → PENDING
// Resultado: 2/4 tareas (50%)
```
